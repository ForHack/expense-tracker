# Pull Request в master

PR создаётся от фиче-ветки в `master` через `gh`. Главное правило: **описание собирается из
реального диффа**, а не из намерения и не из заголовков коммитов. Не прочитал дифф — не пишешь PR.

## Аргументы

Скилл принимает до двух аргументов в любом порядке:

```
/pr "feat(web): add dashboard overview" feature/web-dashboard
/pr feature/web-dashboard
/pr "fix(api): correct summary timezone"
```

- Аргумент, похожий на `<type>(<scope>): <описание>` или просто фразу с пробелами, — **заголовок PR**.
  Проверь его по правилам раздела «Заголовок»; не подходит — поправь и скажи пользователю, что изменил.
- Аргумент без пробелов, похожий на имя ветки (`feature/*`, `fix/*`, …), — **ветка-источник**.
  Если она не текущая, переключись на неё (`git checkout <ветка>`) — не выдумывай дифф чужой ветки.
- Аргументов нет — бери текущую ветку и сформулируй заголовок сам по сути диффа.

Ветка-источник не может быть `master`: PR из `master` в `master` не бывает. Если пользователь
на `master`, остановись и скажи, что нужна фиче-ветка (скилл `commit` её заведёт).

## Порядок действий

1. Проверь исходное состояние:

   ```bash
   git status --short               # незакоммиченное в PR не попадёт
   git fetch origin
   git log --oneline master..HEAD   # какие коммиты войдут
   ```

   Незакоммиченные изменения — спроси пользователя, коммитить их (скилл `commit`) или оставить.
   Коммитов в `master..HEAD` нет — PR создавать не из чего, скажи об этом.

2. **Прочитай дифф** — обязательный шаг:

   ```bash
   git diff master...HEAD --stat    # обзор: какие файлы, на сколько строк
   git diff master...HEAD           # сам дифф
   ```

   Три точки — только свои коммиты, без чужих изменений, приехавших в `master`. Большой дифф
   читай по частям (`git diff master...HEAD -- apps/api`), но прочитай весь.

3. Прогоняй проверки перед PR (из корня репозитория):

   ```bash
   pnpm lint && pnpm typecheck && pnpm build
   ```

   Плюс тесты затронутого пакета (команды Jest — в `apps/api/CLAUDE.md`). Что-то упало —
   не создавай PR, покажи ошибку пользователю.

4. Запушь ветку: `git push -u origin <ветка>`.

5. Сформируй заголовок и тело (разделы ниже). Тело пиши **во временный файл**, например
   `/tmp/pr-body.md`: heredoc в `--body` ломает кириллицу и переносы строк.

6. Создай PR и отдай пользователю ссылку, которую вернул `gh`:

   ```bash
   gh pr create --base master --title '<заголовок>' --body-file /tmp/pr-body.md
   ```

Для UI-изменений напомни пользователю приложить скриншоты вручную — `gh` их не загрузит.

## Заголовок

Ровно по Conventional Commits, как заголовок коммита:

```
<type>(<scope>): <описание>
```

- В повелительном наклонении, **на английском**, со строчной буквы, до 72 символов, без точки.
- Тип и скоуп берутся **по сути изменения целиком** (`feat(web): add dashboard overview`),
  а не копируются с последнего коммита ветки.
- Затронуто несколько пакетов — скоуп опускается.
- Ломающее изменение API-контракта — `!` после скоупа (`feat(api)!: …`).

## Описание

По-русски, markdown, по этому скелету. **Пустые разделы выкидывать, а не оставлять заглушками.**

```markdown
Вводный абзац: что появилось и зачем, 1–3 предложения.

## Что реализовано

- список по фичам, а не по файлам

## Эндпоинты и маршруты

- `POST /api/transactions` — что делает

## Архитектура

- новые слайсы FSD / модули Nest, миграции Prisma, изменения контракта в `shared-types`,
  неочевидные решения с обоснованием

## Проверка

- `pnpm lint`, `pnpm typecheck`, `pnpm build` — прошли
- тесты: ...
- руками: ...

## Осталось за рамками

- сознательно не сделанное, чтобы ревьюер не искал это в диффе
```

Замечания по разделам:

- **Эндпоинты и маршруты** — добавленные/изменённые маршруты Nest и Route Handlers Next
  в виде `МЕТОД /путь — что делает`. Маршрутов в диффе нет — раздела нет.
- **Проверка** — только то, что реально прогнано. Не приписывай пройденные тесты, которых не было.
- **Осталось за рамками** — заглушки, TODO в диффе, сознательно отложенное.
